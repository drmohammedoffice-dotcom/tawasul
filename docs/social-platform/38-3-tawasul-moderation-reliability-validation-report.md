# 38.3 — Content Moderation Reliability Validation (P0)

تاريخ: 4 نوفمبر 2026.  
الأدلة: `ai-service/validation-results/phase38-3-latest.json` — **21 PASS / 0 FAIL / 2 SKIP**.  
منشورات الاختبار الحقيقية في DB (caption `porn`) بحالة **`HIDDEN`** مع قرارات `emergency_sexual` / `fingerprint_match`.

## 1. السبب الجذري الحقيقي

بعد 38.2 كان مسار القرار يعمل جزئياً (المنشورات الأخيرة **مخفية في قاعدة البيانات** والمهام `done`)، لكن التجربة الواقعية فشلت لأن:

### أ) تسريب عرض للمالك يبدو كـ«نشر ناجح»
- `listByAuthor` يعيد للمالك كل الحالات بما فيها `HIDDEN`/`PENDING_REVIEW`.
- `attachMediaUrls` كان يصدر **`secureUrl` دائماً** بغض النظر عن `moderationStatus`.
- شبكة الملف الشخصي (`PostsGrid`) تعرض الصورة مباشرة **بلا شارة حجر**.
- نتيجة المستخدم: صورة إباحية ظاهرة فوراً في بروفايله كأنها منشورة للعامة.

### ب) مسار وسائط يتجاوز الحجر حتى للمالك
- `generateSecureReadUrl` كان يعطي المالك/`uploaderId` رابط القراءة **قبل** فحص حالة المنشور.
- بالتالي حتى لو أُخفي المنشور، بقيت البايتات قابلة للجلب عبر `/media/:id/url`.

### ج) ريلز المؤلف بلا فلتر عام
- `ReelsService.listByAuthor` لم يطبّق `publicModerationWhere` للزوار — تسريب محتمل للريلز غير المعتمدة.

### د) واجهة النشر
- رسالة «تم النشر بنجاح» + فتح المنشور مباشرة، دون إيضاح الحجر.

**ليس** السبب أن المهام لم تُنشأ: سجلات DB تثبت `ModerationJob.status=done` و`ModerationDecision` بـ hide خلال ~100ms بعد النشر. الفشل كان في **عرض/تسريب البايتات** بعد (وأثناء) القرار.

## 2. كيف كان النشر يتجاوز الحماية (منظور المستخدم)

```
رفع → إنشاء PENDING → (قرار HIDDEN سريع)
     → API المالك يعيد المنشور + secureUrl للصورة
     → Profile grid يعرض الصورة كاملة بدون شارة
     → المستخدم يظن أن الحماية لم تعمل
```

حساب آخر لا يرى المنشور في الاستعلام العام (`APPROVED|RESTORED` فقط) — مثبت في الاختبارات — لكن تجربة المالك كانت تكسر الثقة وتعيد عرض المحتوى المحظور.

## 6. الوصول من حساب آخر / روابط مباشرة

- استعلام عام للمؤلف لا يتضمن `HIDDEN`.
- `GET /api/posts/:hiddenId` بدون جلسة → 401.
- `GET /api/media/:id/url` بدون جلسة → 401/404.
- بعد الإصلاح: حتى المالك لا يحصل على `secureUrl` لمنشور غير `APPROVED`.

## 7. إعادة تشغيل الخادم

- المهام المعلّقة تُعاد عبر `ModerationMaintenance` / `processBatch`.
- الحالة تبقى غير عامة حتى قرار صريح؛ لا auto-approve عند الفشل.
- Nest أُعيد تجميعه بنجاح بعد التعديلات (0 أخطاء TypeScript).

## 8. ثغرات متبقية (صريحة)

1. اختبار يدوي بحسابين في المتصفح لم يُنفَّذ آلياً في هذه الجولة (SKIP موثّق) — يُفضَّل تأكيده من المشغّل بعد Hard Refresh.
2. فيديو NSFW يعتمد على `ffmpeg`/`ffprobe` على PATH؛ إن غابا → `media_scan_incomplete` (حجر، لا موافقة).
3. Whisper/OCR للفيديو اختياري؛ غياب التفريغ لا يعني سلامة بصرية (الإطارات إلزامية للفيديو).

## 9. شرط الإغلاق

- المحتوى المخالف في DB = `HIDDEN` ولا يظهر للعامة عبر الاستعلامات العامة.
- بايتات الوسائط غير المعتمدة لا تُصدَّر في API المالك ولا عبر `/media/:id/url`.
- الواجهة تعرض شارة حجر بدل الصورة.
- المحتوى الطبيعي ما زال يُوافق عليه فقط بعد فحص مكتمل (`APPROVED`).
